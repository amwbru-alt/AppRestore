# АппВерни

АппВерни — новое имя сервиса на базе AppRestore. Сохранены исходный движок,
GPL-3.0 и уведомления об авторах. Имя GitHub-репозитория, Python-пакетов,
старых каталогов и файлов релизов оставлено для совместимости.

Добавлены отдельные `/login` и `/register`, каталог `/install`, история
`/orders`, админ-панель `/admin`, SQLite и очередь исполнителя.
Пароль Apple ID в веб-формы не вводится. Учетная запись сервиса — отдельная.

## Быстрый запуск сервиса

Python 3.10–3.13. Веб-часть использует только стандартную библиотеку:
из корня исходников её можно запустить без установки Qt или pymobiledevice3.

```bash
python -m appverni --database data/appverni.sqlite3 create-admin --email admin@example.com
python -m appverni --database data/appverni.sqlite3 serve --dev-http
```

Пароль администратора вводится скрыто, минимум 12 символов. У первого
зарегистрировавшегося пользователя **нет** административных прав.
Администратор создается локальной командой выше. Для уже зарегистрированного
аккаунта: `python -m appverni promote-admin --email admin@example.com`.
Указывайте один и тот же `--database` при всех административных командах.

Откройте `http://127.0.0.1:8080`. Войдите администратором, добавьте карточки:
название, App Store ID (8–12 цифр), описание и HTTPS-ссылка на фото или
PNG/JPEG до 2 МБ. Карточку можно редактировать и скрывать. App Store ID после
создания неизменяем: другой ID означает новое приложение. Действующие
заказы сохраняют исходный ID и название, даже если карточку изменили.

Для проверки пользовательского сценария зарегистрируйте отдельный аккаунт.
Подключите Apple ID по email. На первом открытии каталога создается задача
полной проверки истории. До её завершения установка недоступна; кнопки
показывают ожидание, а не ложное «можно установить».

## Настройка настоящего исполнителя

Сервер не может установить приложение на iPhone из браузера. На доверенном
компьютере оператора нужен работающий исходный движок AppRestore,
**ipatool с патчами проекта**, авторизованный Apple ID и iPhone по USB.
Подготовка зависимостей и ipatool: [RUN-FROM-SOURCE.md](RUN-FROM-SOURCE.md).

Каждый исполнитель закреплен за одной связью пользователя сервиса и Apple ID.
В `/admin` в таблице «Пользователи и проверка Apple ID» указан ID этой связи.
Создайте секрет **на сервере**, где находится база сервиса:

```bash
python -m appverni --database data/appverni.sqlite3 provision-worker --account 1 --token-file data/worker-1.key
```

Секрет создается в новом файле и не печатается в терминале. Передайте файл
на доверенный компьютер оператора защищенным способом. Это административный
секрет: **не выдавайте его клиентам и не включайте в сборку для скачивания**.
Исполнитель считается доверенным источником проверки, а не доказательством,
полученным от произвольного пользовательского браузера.

На компьютере исполнителя:

1. Используйте отдельного пользователя ОС/профиль для каждого Apple ID,
   отдельный каталог данных и выделенный iPhone. Общая связка ключей ipatool
   между разными клиентами не допускается. Пока работает исполнитель,
   не переключайте Apple ID в другом окне программы.
2. Выполните `python apprestore.py auth --email you@icloud.com` и завершите
   вход, включая 2FA. Пароль Apple ID получает локальный ipatool.
3. Узнайте UDID: `python apprestore.py devices`.
4. Запустите исполнитель; пароль **локальной связки ключей**, если нужен,
   вводится скрыто и передается ipatool по stdin, а не через аргументы:

```bash
python -m appverni worker --url https://your-service.example --token-file data/worker-1.key --apple-id you@icloud.com --udid YOUR_DEVICE_UDID --state-file data/worker-1-state.json
```

При локальном запуске допустим `--url http://127.0.0.1:8080`. Для удаленного
сервиса требуется HTTPS, перенаправления запрещены. Режим `--once` обрабатывает
одну задачу и завершает процесс. Исполнители опрашивают очередь каждые 3 секунды.

Исполнитель сверяет email в настоящей сессии ipatool с назначенным Apple ID
перед задачей и после проверки/загрузки. Получает **всю** историю покупок
через `iter_purchases`, включая все страницы; частичный результат не принимается.
Результаты сохраняются в SQLite отдельно по связи с Apple ID, в том числе
пустой успешно проверенный список. Повторное открытие страницы не вызывает
новый запрос Apple. Добавленная позднее карточка сравнивается с сохраненным
полным списком. Для нового Apple ID нужна отдельная проверка. Кнопка
«Обновить историю Apple» запускает явную повторную проверку (не чаще раза
в минуту). Сбой обновления сохраняет прошлый успешный снимок.

**Ограничение Apple:** история покупок подтверждает, что приложение ранее
было получено на Apple ID, включая бесплатные приложения. Она не доказывает
фактическую установку на конкретное устройство. Даже для приложения из
истории Apple может больше не отдавать IPA. Интерфейс сообщает об этом;
успех установки не подменяется успехом проверки истории.

## Тариф и заказы

Первая **успешная установка** на аккаунт сервиса — бесплатно, далее 100 ₽.
Подарок резервируется атомарно при создании заказа: одновременные клики
и разные Apple ID не дают несколько бесплатных установок. Повторный клик
возвращает текущий незавершенный заказ. В запросе отправляется ID карточки,
сервер сам получает её App Store ID и стоимость; исполнитель получает
именно этот App Store ID. Подставленная браузером цена игнорируется.

Платный заказ получает `awaiting_payment` и **не попадает к исполнителю**.
Платежный шлюз, списания и имитация оплаты не реализованы, как и запрошено.
Будущий платежный обработчик должен подтверждать сумму/валюту на сервере,
проверять подпись и уникальность события, а затем атомарно переводить
соответствующий заказ в очередь. Клиентский редирект оплаты для этого не годится.

Бесплатный заказ проходит `queued → running → succeeded` после того, как
исходный движок подтвердил приложение на назначенном iPhone. При сбое до
установки заказ становится `failed` и подарок снова доступен. Ранее созданный
платный ожидающий заказ при повторном клике может воспользоваться освободившимся
подарком. При неясном результате после обращения к устройству — `uncertain`:
автоматической повторной установки нет, подарок остается зарезервирован.
Оператор проверяет устройство и фиксирует результат локальной командой:

```bash
python -m appverni --database data/appverni.sqlite3 resolve-order --id ORDER_ID --result failed --reason "Проверено на устройстве: приложение не установлено"
```

Для подтвержденной установки используйте `--result succeeded`. Команда
принимает только заказы `uncertain`, записывает основание и аудит. Не меняйте
базу вручную. Перед повторным запуском исполнителя сохраняйте его state-файл:
он предотвращает повторную установку после обрыва связи или перезапуска.
Секрет в state-файл не записывается. Один state-файл — один исполнитель.

## Ошибка ipatool при входе в Apple ID

Сообщение «ipatool не найден» означает, что программа не обнаружила отдельный
исполняемый компонент. До обращения к паролю/Apple этот вход не дошел.

- Windows, готовая программа: распакуйте **полный** GUI-архив в отдельную
  папку, запускайте `AppRestore.exe` оттуда. Рядом должен быть `ipatool.exe`
  (также поддерживается `bin/ipatool.exe`). Не копируйте один EXE из архива.
- Исходники: каталог `bin` по умолчанию не включен в Git. Соберите ipatool
  по [RUN-FROM-SOURCE.md](RUN-FROM-SOURCE.md) и положите его в
  `bin/ipatool.exe` (Windows) или `bin/ipatool` (macOS).
- macOS: у `bin/ipatool` должно быть право запуска: `chmod +x bin/ipatool`.
- Для нестандартного расположения задайте полный путь
  `APPRESTORE_IPATOOL_PATH`. Если заданного файла нет, поиск не переключается
  молча на другую сборку. Нужна сборка с патчами проекта, а не случайный EXE.

Пример в PowerShell перед запуском из того же окна:

```powershell
$env:APPRESTORE_IPATOOL_PATH = 'C:\AppVerni\bin\ipatool.exe'
python -m apprestore_gui.app --ui quick
```

Замените путь на настоящий. Если антивирус удалил файл, проверьте его журнал
и контрольную сумму исходного архива; не отключайте защиту для неизвестного EXE.

## Эксплуатация

`serve` — встроенный WSGI-сервер для разработки/проверки. Для эксплуатации
экспортируйте `appverni.web.Application('/absolute/path/service.sqlite3')`
из WSGI-модуля и используйте производственный WSGI-сервер за HTTPS-прокси.
`secure=True` включено по умолчанию (Secure, HttpOnly, SameSite cookies).
`--dev-http` отключает Secure только на localhost. Ограничьте размер тела
запроса 3 МБ, время чтения и частоту запросов на прокси; прокси должен
корректно задавать WSGI REMOTE_ADDR, а не доверять произвольному заголовку IP.
Отдельно ограничьте доступ к `/worker/*` компьютерами оператора.

База создается при первом запуске (schema version 1), пароли хешируются
scrypt с индивидуальной солью. Сессии и токены исполнителя хранятся в базе
в виде SHA-256 от случайного секрета. POST-формы защищены CSRF, SQL использует
параметры, HTML экранируется, действия с каталогом и заказами аудируются.
Данные, фото и секреты не должны попадать в Git. Резервируйте SQLite и
соседнюю папку `images` согласованно; данные привязаны к Apple ID и email.
Не удаляйте state-файлы активных исполнителей.

В этой версии нет восстановления пароля, подтверждения email и платежного
провайдера. Перед публичным запуском потребуется их интеграция и проверка
на настоящих устройствах Windows/macOS. Новая веб-часть не встроена в старую
GUI-сборку: запускается отдельной командой. Исходный CLI и локальная установка
AppRestore сохранены для оператора; тариф применяется к заказам веб-сервиса,
а не является DRM-защитой открытого исходного движка.

## Проверки

```bash
python -m unittest tests.test_appverni -q
python -m pytest -q tests/test_appverni.py tests/test_paths.py tests/test_ipatool_api.py tests/test_gui_errors.py tests/test_frozen_runtime.py tests/test_gui_packaging.py
```

В тестах есть конкурентное резервирование подарка, повторные клики,
изоляция пользователей/Apple ID/исполнителей, CSRF, роли, загрузка фото,
кэш полной истории, ошибки/частичные результаты Apple, блокировка платных
задач и подтверждение/неопределенность установки. Физический iPhone и вход
в Apple ID в автоматических тестах заменены управляемыми адаптерами.
