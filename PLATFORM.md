> **Регистрация обновлена:** аккаунт AppRevive создаётся без письма, сразу доступен вход по паролю. Подтверждение принадлежности Apple ID и сброс забытого пароля остаются отдельными действиями. Ранее неподтверждённые пользователи тоже могут войти со своим прежним паролем.

> Актуальная схема сайта: покупка промокодов принадлежит аккаунту AppRevive и не требует Apple ID. Привязка и активация Apple ID убраны из обычного кабинета. Разделы ниже о старой привязке относятся к совместимости нативного приложения, а не к оформлению покупки на сайте.


> **Текущий временный режим — HTTP:** [запуск на IP и сборка Mac/Windows](HTTP-TEMP.md). Эта инструкция заменяет прежнее обязательное требование HTTPS.

# AppRevive 0.5.0: сервер, кабинеты, платежи и сборка

Изменения нужно выпускать согласованно: новый сервер закрывает частные API авторизацией, поэтому клиенты 0.4.0 потребуется обновить. Сервер хранит старые балансы, установки, использованные коды и приглашения. Не удаляйте базу при переходе. Выполните резервное копирование перед миграцией.

## 1. Что включено

- `/` — сайт приложения; `/account` — регистрация, вход, подтверждение почты, сброс пароля, привязка Apple ID, баланс, история, покупка и активация кодов, партнёрская статистика.
- `/admin` — доступ только роли admin: каталог и группы банков, последние пользователи/заказы/операции, ручное подтверждение оплаты, возвраты, разрешение зависших восстановлений, комиссия и учёт выплат. Все административные изменения оставляют записи начала/завершения в журнале.
- Настройки настольного приложения — «Аккаунт AppRevive и баланс»: вход, почтовая привязка, остаток, коды, покупка через защищённую страницу платёжного провайдера. Пароль Apple ID вводится отдельно, как прежде, в окне Apple.
- Проверка подключения выбранного устройства, инструментов и доступного места перед восстановлением; отдельное окно подтверждения до резервирования попытки. Если размер удалённого приложения неизвестен, программа не обещает, что оно поместится.
- У одного Apple ID один серверный баланс, в том числе после удаления программы и очистки кеша. Идентификатор остался прежним. Почтовое подтверждение защищает доступ к балансу; оно не заменяет проверку покупок у Apple.
- Проверка обновлений при запуске. Скачивание и замена требуют согласия пользователя, проверяется SHA-256, неудачная замена откатывается.

## 2. Домен и HTTPS

Старый `http://185.173.93.200:3000` больше не подходит для входа, токенов и платежей. Приложение и кабинет откажутся передавать пароль на публичный HTTP. Нужен принадлежащий вам домен, например поддомен `revive.ВАШ-ДОМЕН`; пример ниже `revive.example.com` **замените своим настоящим адресом**.

1. Создайте DNS A-запись домена на `185.173.93.200`.
2. На сервере откройте входящие TCP 80 и 443. Node должен слушать `127.0.0.1:3000`; доступ извне к 3000 закройте.
3. Установите Caddy по [официальной инструкции](https://caddyserver.com/docs/install). Скопируйте содержимое `server/node/deploy/Caddyfile.example` в `/etc/caddy/Caddyfile`, замените домен.
4. Проверьте и перезагрузите:

```bash
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

Caddy завершает TLS и сам управляет сертификатом домена. Приложение доверяет заголовку HTTPS только от локального прокси. `DEV_ALLOW_INSECURE_AUTH=true` предназначен исключительно для изолированной локальной разработки и не включается на сервере.

## 3. Обновить Node и MySQL

На сервере нужен Node.js 24 LTS либо совместимый 25/26 и npm. На компьютерах пользователей Node/MySQL не устанавливаются.

```bash
git clone --branch codex/apprevive-icons https://github.com/amwbru-alt/AppRestore.git AppRevive
cd AppRevive/server/node
npm ci
cp .env.example .env
chmod 600 .env
nano .env
```

Для существующего клона сначала сохраните изменения `.env`, обновите ветку через `git pull --ff-only`, выполните `npm ci`; **не заменяйте существующий `.env` пустым шаблоном**. Команды ниже запускаются из `server/node`.

Заполните только на сервере:

```dotenv
HOST=127.0.0.1
PORT=3000
ALLOW_HTTP=false
PUBLIC_URL=https://revive.example.com
DEV_ALLOW_INSECURE_AUTH=false
DB_HOST=shuloquaticu.beget.app
DB_PORT=3306
DB_USER=apple
DB_NAME=apple
DB_PASSWORD=ВАШ_ПАРОЛЬ_БАЗЫ
APP_ENV=production
PAYMENTS_ENABLED=false
PAYMENTS_TEST_MODE=false
```

Пароль не добавляйте в Git, `api_settings.json`, GUI или GitHub Actions variable. При наличии сертификата MySQL от провайдера задайте `DB_SSL_CA=/путь/к/ca.pem`. Учётная запись должна иметь права создавать таблицы при миграции. Схемы совместимы с MySQL 5.7; новую базу создавать не требуется.

Остановите прежний процесс Node, сделайте резервную копию БД, затем:

```bash
node --env-file=.env src/migrate.mjs
node --env-file=.env src/manage.mjs import-groups catalog-groups.json
npm start
```

Миграция последовательно применяет `server/promo/*-schema.sql` и исходную `schema.sql`, добавляет таблицы через `CREATE TABLE IF NOT EXISTS`, не обнуляет данные. При ошибке остановитесь и исправьте доступ/схему. Не запускайте новый процесс параллельно со старым на том же порту. Для постоянной работы используйте уже настроенный systemd/PM2, изменив рабочий каталог и команду на указанные выше.

Проверка после запуска и настройки Caddy:

```bash
curl --fail https://revive.example.com/health
curl --fail https://revive.example.com/v3/status
```

`/health` подтверждает работу процесса; доступность новых таблиц проверяется при запуске. Запрос `/v3/status` дополнительно читает настройки из базы; регистрация проверяет работу почты. Временные неопределённые результаты установки не возвращаются автоматически: администратор должен проверить результат на устройстве и выбрать успешное/неуспешное завершение в админке.

## 4. Почта, регистрация и администратор

Реализована отправка через [Resend](https://resend.com/docs/api-reference/emails/send-email). Подтвердите домен отправителя у провайдера и добавьте в серверный `.env`:

```dotenv
RESEND_API_KEY=КЛЮЧ_ТОЛЬКО_НА_СЕРВЕРЕ
MAIL_FROM="AppRevive <noreply@revive.example.com>"
```

Перезапустите Node. Ссылка подтверждения действует 15 минут, одноразовая. При подтверждении регистрации пользователь задаёт пароль заново; пароль сервиса — минимум 12 символов. Не используйте пароль Apple. Сброс пароля отзывает существующие сеансы. Токены и пароли не попадают в ссылки запроса/журналы API; токен письма находится во фрагменте URL.

Создать/обновить администратора на сервере, Bash, пароль скрыт при вводе:

```bash
read -r -s -p 'Новый пароль AppRevive (12+ символов): ' apprevive_admin_password
echo
printf '%s' "$apprevive_admin_password" | node --env-file=.env src/manage.mjs create-admin admin@ВАШ-ДОМЕН
unset apprevive_admin_password
```

Войдите в `https://ВАШ-ДОМЕН/admin`. Команда подтверждает почту администратора, назначает роль и отзывает его старые сессии. Не передавайте пароль параметром команды.

Пользователь регистрируется в кабинете или GUI. Если почта сервиса совпадает с Apple ID, подтверждённый адрес доступен сразу. Если отличается — привязывает Apple ID, получает письмо на его почту и подтверждает из того же аккаунта AppRevive. Если адрес уже привязан к другому аккаунту, автоматический перенос запрещён. Ранее накопленные балансы остаются у прежнего идентификатора Apple ID.

В GUI сессия живёт только в памяти: после перезапуска нужно войти в сервис снова. Очистка аккаунтов Apple не сбрасывает серверные установки и подарок. В браузере используется Secure/HttpOnly/SameSite cookie; сессия действует до 7 дней.

## 5. Приём оплаты ЮKassa

До настройки покупка отключена. Нужны действующий магазин и секретный ключ [ЮKassa](https://yookassa.ru/developers/api). Проверьте параметры чека со своей настройкой магазина: код НДС обязателен, при необходимости код системы налогообложения. Наименование позиции — код восстановления AppRevive, предмет расчёта `service`, способ `full_payment`. Не включайте реальные платежи, пока эти параметры не подходят вашему договору и способу фискализации.

```dotenv
PAYMENTS_ENABLED=true
YOOKASSA_SHOP_ID=ВАШ_SHOP_ID
YOOKASSA_SECRET_KEY=СЕКРЕТНЫЙ_КЛЮЧ
PAYMENT_VAT_CODE=КОД_НДС
PAYMENT_TAX_SYSTEM_CODE=
```

В настройках уведомлений ЮKassa укажите `https://ВАШ-ДОМЕН/v3/payment/webhook` и события `payment.succeeded`, `payment.canceled`, `refund.succeeded`. Перезапустите Node. Статус `/v3/status` должен показывать `payments_enabled:true`.

Сумма рассчитывается сервером: 100 рублей за код, 1–100 кодов в онлайн-заказе. Данные карты вводятся у провайдера. После оплаты коды видны в кабинете/GUI, пользователь активирует код для выбранного Apple ID. Код даёт одну попытку; первый подарок выдаётся сервером только один раз для Apple ID.

Переход по return_url и содержимое webhook сами по себе не подтверждают оплату: сервер запрашивает реальный статус у ЮKassa, сверяет сумму, валюту и идентификатор. Повторные уведомления/запросы не создают новые заказы и коды. После сетевого сбоя используйте «Проверить оплату» у существующего заказа; не создавайте второй. Если удалённый платёж не удалось связать с заказом больше 23 часов, требуется ручная сверка, новый платёж автоматически не создаётся.

Сначала проверьте покупку тестовым магазином **на отдельном staging-сервере и отдельной базе**:

```dotenv
APP_ENV=staging
PAYMENTS_TEST_MODE=true
```

В production тестовые платежи отклоняются. В staging выполните успешную/отменённую оплату, повторное уведомление, восстановление после сбоя и полный возврат. Нельзя направлять staging в production-базу. Реальный тестовый/боевой платёж в ходе разработки автоматически не выполнялся.

Админка позволяет сверить статус и инициировать **полный** возврат через провайдера. Неиспользованные коды заказа аннулируются, партнёрское начисление отменяется. Ранее активированный код не отнимает уже выданный баланс — это сохраняет прежнее правило проекта. Частичные возвраты автоматически не рассчитываются и требуют ручного разбора; webhook вернёт ошибку до устранения расхождения. До разбора приостановите партнёрские выплаты. Не используйте кнопку «ручной возврат» для заказов ЮKassa.

Ручное подтверждение оплаты оставлено для администратора: укажите покупателя, число кодов, сумму в копейках и уникальную ссылку на фактически полученную оплату, подтвердите флажком. Это не автоматическая проверка перевода; ответственность за подтверждение у оператора.

## 6. Партнёрские начисления и выплаты

Покупатель вводит код пригласившего **до первой покупки**. Привязка неизменяема, приглашение самого себя запрещено. Статистика считает оплаченные покупки и коды; возвраты исключаются. Продажи без пригласившего не приписываются партнёру задним числом.

В админке задайте процент и срок удержания. По умолчанию комиссия 0%, удержание 14 дней — деньги не обещаются до установки условий. Новая политика применяется только к будущим продажам; старые записи не пересчитываются. Суммы хранятся в целых копейках, округление комиссии вниз.

У выплаты три состояния: pending резервирует доступные деньги, paid фиксирует выполненный перевод, cancelled снимает резерв. Используйте уникальный внешний reference перевода. Нельзя зарезервировать больше доступного. **Перевод денег партнёру выполняется оператором отдельно**; автоматическое перечисление на карту не подключено. После подтверждения фактического перевода отметьте paid. Не отмечайте paid заранее. Возврат после выплаты создаёт отрицательный доступный остаток, погашаемый будущими начислениями.

Дашборд показывает последние 200 записей, личная история/заказы — последние 100. Полная история остаётся в MySQL. Не удаляйте записи выплат и аудита для «исправления» баланса.

## 7. Каталог и группы банков

В `/admin` редактируются название, HTTPS-ссылка на иконку, доступность и список вариантов каждого банка. В списке вариантов строка имеет вид `ID; название; HTTPS-иконка`. Пользователь видит банк, клиент сопоставляет варианты с его реальной историей Apple и предлагает найденное ранее приобретённое приложение. Добавление ID в каталог само по себе не доказывает покупку.

Подробнее: [BANK-GROUPS.md](BANK-GROUPS.md), [CATALOG.md](CATALOG.md). Не запускайте повторный импорт стандартных групп после своих правок: импорт заменяет список групп, поэтому сначала экспортируйте/сохраните собственный файл.

## 8. Сборка Mac и Windows через терминал на Mac

В каталоге Git-клона:

```bash
git switch codex/apprevive-icons
git pull --ff-only
gh auth status
```

Укажите **настоящий HTTPS-адрес** API. Это публичная настройка, не секрет:

```bash
gh variable set APPREVIVE_PUBLIC_API_URL --repo amwbru-alt/AppRestore --body 'https://revive.example.com'
gh workflow run gui-build.yml --repo amwbru-alt/AppRestore --ref codex/apprevive-icons
gh run list --repo amwbru-alt/AppRestore --workflow gui-build.yml --branch codex/apprevive-icons --limit 3
```

Вместо `revive.example.com` подставьте свой домен. Без HTTPS-переменной сборка 0.5.0 завершится с понятной ошибкой. Для одной сборки можно передать `-f service_api_url=https://ВАШ-ДОМЕН`. В GitHub хранится только адрес; никаких DB/Resend/YooKassa-паролей в GUI workflow не добавляется.

Скопируйте ID нового **run**, не job, и выполните (пример ID замените):

```bash
APPREVIVE_RUN_ID=НОВЫЙ_ID
gh run watch "$APPREVIVE_RUN_ID" --repo amwbru-alt/AppRestore --exit-status
gh run download "$APPREVIVE_RUN_ID" --repo amwbru-alt/AppRestore --name AppRevive-GUI-macOS --dir "$HOME/Downloads/AppRevive-macOS-$APPREVIVE_RUN_ID"
gh run download "$APPREVIVE_RUN_ID" --repo amwbru-alt/AppRestore --name AppRevive-GUI-Windows --dir "$HOME/Downloads/AppRevive-Windows-$APPREVIVE_RUN_ID"
```

Внутри артефактов ZIP для каждой системы. Mac запускает `AppRevive.app`, Windows — `AppRevive/AppRevive.exe` из полностью распакованной папки. В `.tar.gz` ipatool не нужно запускаться: его содержит сборка. Нужен запас диска для временного ZIP и распаковки. Обычный GUI build — тестовая сборка, не подписанный публичный выпуск.

Для локальной сборки сначала замените `base_url` в `apprevive_core/api_settings.json` своим HTTPS-адресом, затем используйте команды [BUILDING.md](BUILDING.md). Не добавляйте туда учётные данные. Готовому GUI можно задать тот же адрес через пользовательский `api.json` по путям из INSTALL-GIT.md; приоритет пользовательского файла выше встроенной настройки.

## 9. Подписанный публичный выпуск и обновления

Подготовлен отдельный `gui-signed-release.yml`. Он проверяет, что исходный GUI build завершился успешно, принадлежит этому репозиторию и тому же коммиту; версия совпадает с `pyproject.toml`. Публикация происходит только после успешной подписи обеих систем, health-check и notarization Mac. Фактически подписанный выпуск не создавался без ваших сертификатов.

Новый workflow должен присутствовать в основной ветке репозитория, чтобы GitHub разрешил его ручной запуск. Если он пока только в `codex/apprevive-icons`, сначала включите этот файл в основную ветку через проверенный PR. Само приложение можно собирать существующим GUI build из рабочей ветки.

Создайте защищённое GitHub Environment `release`, ограничьте разрешённые ветки/доступ и добавьте **только в Secrets окружения**:

| Secret | Значение |
|---|---|
| WIN_CERT_BASE64 | PFX сертификата code signing вместе с закрытым ключом, base64 |
| WIN_CERT_PASSWORD | Пароль PFX |
| MAC_CERT_BASE64 | Developer ID Application сертификат + закрытый ключ в P12, base64 |
| MAC_CERT_PASSWORD | Пароль P12 |
| MAC_SIGN_IDENTITY | Полное имя Developer ID Application identity |
| APPLE_API_KEY_BASE64 | Закрытый App Store Connect API-ключ `.p8`, base64 |
| APPLE_API_KEY_ID | Key ID для notarytool |
| APPLE_API_ISSUER | Issuer ID |

Не публикуйте эти файлы/значения в репозитории, чатах или логах. Windows-вариант этого workflow рассчитан на экспортируемый PFX. Если ваш сертификат хранится только в аппаратном токене/HSM или вы используете облачную подпись, нужен соответствующий провайдер и его интеграция вместо шага импорта PFX. Наличие кода workflow само по себе не выдаёт доверенный сертификат.

После успешного GUI build **того же коммита**, заменив ID:

```bash
gh workflow run gui-signed-release.yml --repo amwbru-alt/AppRestore --ref codex/apprevive-icons -f build_run_id=ID_УСПЕШНОЙ_СБОРКИ -f version=0.5.0
```

Готовый выпуск `v0.5.0` содержит две подписанные ZIP и `SHA256SUMS.txt`, его увидит обновлятор. Существующий релиз не перезаписывается: для следующего выпуска поднимайте версию согласованно в проекте. Для загрузок с сайта укажите `DOWNLOAD_MAC_URL`/`DOWNLOAD_WINDOWS_URL` на ZIP этого релиза или положите файлы в `server/node/downloads` под именами из WEBSITE.md.

## 10. Проверка перед включением production

Проверьте регистрацию и письмо, вход GUI, подтверждение другого Apple ID, сохранность прежнего баланса, запрет чужого баланса, первую бесплатную попытку, отказ/сбой установки без потери попытки, тестовую покупку/выдачу ровно одного комплекта кодов, полный возврат, партнёрскую комиссию и резерв выплаты. Не возвращайте попытку вручную, пока установка ещё выполняется.

Автотесты покрывают серверные состояния и GUI с подменёнными устройствами/сетью. Настоящее устройство Apple, реальные переводы, почтовая доставка, сертификаты подписи и notarization требуют проверки в вашем окружении. Прямого MySQL-доступа из Mac/Windows нет: только серверный API.

## Регистрационная реферальная система

Теперь код вводится непосредственно при регистрации AppRevive. Ссылка `/register?ref=RVP-…` сохраняет код при переходе на форму. После регистрации сайт выполняет вход и открывает кабинет. В отличие от прежнего сценария, приглашённый сразу появляется у партнёра, без покупки и без Apple ID. Коды без почтового подтверждения регистрации поддерживаются. Неверный код откатывает создание аккаунта.

Новая таблица `apprevive_user_referrals` хранит постоянную связь пользователя с пригласившим. Позже подтверждённый Apple ID позволяет связать реальные покупки с этим пользователем. Повторные платежные уведомления не дублируют заказ/комиссию; полный возврат отменяет комиссию. Исторический пригласивший Apple ID и покупки, сделанные до приглашения, не переписываются. Старые ручные привязки продолжают работать; регистрации и привязки Apple ID показаны отдельно в админке. Партнёру доступны список регистраций, покупки и начисления по каждому рефералу. Личные email рефералов партнёрам не раскрываются.

Процент администратор задаёт в разделе партнёрских начислений. Ставка применяется только к новым подтверждённым заказам. При ставке 0 кабинет прямо показывает, что вознаграждение ещё не установлено. Выплаты не переводят деньги автоматически: администратор резервирует сумму, выполняет внешний перевод и подтверждает его.

Развёртывание на существующем сервере:

```bash
git switch codex/apprevive-icons
git pull --ff-only
cd server/node
npm ci
node --env-file=.env src/migrate.mjs
```

Затем перезапустите существующий Node-процесс в PM2/systemd или терминале. Таблицы/данные не удалять, реквизиты MySQL остаются в существующем `.env`. Нативные установщики для обновления сайта пересобирать не нужно.

## Рабочий кабинет и администрирование

В кабинете появился раздел безопасности: список активных сессий сайта и приложения, завершение выбранного/всех остальных входов, смена пароля AppRevive с проверкой текущего. Смена пароля сохраняет текущий вход, отключает остальные сессии и старые ссылки сброса пароля. Управление сессиями ограничено владельцем; сырые токены API не выдаются. Это не меняет пароль Apple ID и не сбрасывает балансы/покупки.

Пользователи и заказы в админке ищутся по всей базе, с фильтрами и постраничной загрузкой по 25 записей. Карточки показателей считаются по всей базе; продажи учитывают оплаченные заказы и исключают полностью возвращённые. CSV выгружает только текущую страницу с активными фильтрами; ячейки защищены от выполнения формул в Excel. Остальные таблицы админки пока ограничены последними 200 записями.

Открытый кабинет обновляет партнёрку, заказы и баланс раз в 30 секунд. Фоновое обновление приостановлено в скрытой вкладке, без сети или при заполнении полей; после возврата/восстановления сети выполняется снова. Это периодический запрос к API, не WebSocket. Истёкшая сессия возвращает форму входа; старые ответы не должны подменять данные после выхода или смены Apple ID.

Новые маршруты: GET `/v3/security/sessions`, POST `/v3/security/revoke`, POST `/v3/security/password`; администратору — GET `/v3/admin/users`, `/v3/admin/orders` (параметры `page`, `size`, `q`, `state`) и `/v3/admin/metrics`. Доступ к административным данным проверяется сервером. Новых таблиц для этой части не требуется; порядок обновления сервера остаётся `git pull`, `npm ci`, существующая миграция и перезапуск Node.

## Покупка и статусы промокодов без Apple ID на сайте

Сайт создаёт внутреннего покупателя по ID сервисного пользователя (`apprevive_user_buyers`). POST `/v3/checkout` принимает количество и request_id; переданный клиентом account_id игнорируется. Apple ID для покупки не запрашивается и не проверяется. Пригласивший берётся из регистрации пользователя; исторические партнёрские привязки по возможности сохраняются. Сами коды могут быть переданы исполнителю и активированы в приложении на другом подтверждённом Apple ID.

Новые выпущенные коды сохраняются в `apprevive_issued_codes` одновременно с заказом. После активации запись удаляется из пула доступных кодов, но остаётся в истории покупателя. GET `/v3/orders` отдаёт только собственные коды покупателя с `activation_status`: `unused` («Не активирован»), `activated` («Активирован», с датой), `invalidated` («Аннулирован» после возврата неактивированного кода), `unavailable` (неизвестное историческое состояние, нужна проверка). Статус «Активирован» означает погашение кода приложением, а не успешную установку конкретного приложения. Apple ID исполнителя покупателю не раскрывается.

Миграция сохраняет текст всех существующих неиспользованных кодов. Текст старых кодов, активированных до обновления, восстановить из хеша невозможно: показываем статус и идентификатор без выдуманного текста кода. Доступ к полным кодам ограничен владельцем заказа.

Перед обновлением сделайте резервную копию БД. Обновите исходники, выполните `npm ci`, `node --env-file=.env src/migrate.mjs` из `server/node` и перезапустите Node. Новая схема совместима с прежними заказами; не удаляйте таблицы и балансы. Нативные приложения для этого обновления пересобирать не требуется.
