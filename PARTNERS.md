# Партнёрская программа AppRevive

## Как это работает

На Mac и Windows откройте **Настройки → Партнёрская программа** после входа в Apple ID.
Скопируйте личный код `RVP-…` и отправьте приглашённому. Он вводит его в том же
разделе **до первой покупки**. Привязка сохраняется в MySQL, переживает очистку
аккаунтов и переустановку приложения; сменить пригласившего нельзя. Ввод того же
кода повторно безопасен. Собственный код запрещён. Учёт ведётся по Apple ID,
а не по устройству: разные Apple ID одного человека считаются разными аккаунтами.

Партнёр видит число приглашённых аккаунтов, покупателей, оплаченных заказов,
купленных кодов и общую сумму покупок. Чужие Apple ID и сами коды покупок ему
не показываются. Сумма продаж **не является заработком партнёра**.

Партнёрский код `RVP-…` не является кодом восстановления `RV-…`. Его привязка
не начисляет восстановлений. Покупка и активация — разные события: даже если
код подарили другому человеку, заказ относится к Apple ID покупателя и его
пригласившему. Повторная активация не увеличивает статистику продаж.

## Обновить сервер

Из корня существующего git-клона сервера:

```bash
git switch codex/apprevive-icons
git pull --ff-only
mysql --host=shuloquaticu.beget.app --port=3306 --user=apple --password --database=apple < server/promo/schema.sql
mysql --host=shuloquaticu.beget.app --port=3306 --user=apple --password --database=apple < server/promo/accounts-schema.sql
mysql --host=shuloquaticu.beget.app --port=3306 --user=apple --password --database=apple < server/promo/partners-schema.sql
cd server/node
npm ci --ignore-scripts
sudo systemctl restart apprevive-api
```

При ручном запуске вместо `systemctl` остановите старый процесс и запустите
`npm start`. Пароль базы вводите в приглашении mysql; `.env` сохраняется.
Через панель MySQL можно импортировать те же SQL-файлы, если mysql CLI нет.

После обновления сервера пересоберите клиенты:

```bash
gh workflow run gui-build.yml --repo amwbru-alt/AppRestore --ref codex/apprevive-icons
```

## Как фиксировать реальные покупки сейчас

Платёжный шлюз ещё не подключён. **После проверки фактической оплаты**
администратор на сервере выполняет команду из `server/node`:

```bash
node --env-file=.env src/manage.mjs record-purchase BUYER_ID 2 20000 bank-20261019-0001
```

Замените `BUYER_ID` на 64-символьный ID из окна покупателя.
`2` — количество кодов, `20000` — **общая сумма в копейках** (200 рублей),
`bank-20261019-0001` — уникальный номер именно этой оплаты. Не используйте новый
номер для повтора одной и той же оплаты. Разрешены латинские буквы, цифры,
точка, дефис, подчёркивание и двоеточие; максимум 128 символов.

Команда атомарно создаёт оплаченный заказ, фиксирует партнёра и выпускает
указанное число кодов восстановления. Результат содержит `order_id` и
`unused_codes`. Передайте коды покупателю вручную. Они не привязаны к аккаунту
для активации: это передаваемые коды восстановления, покупатель учитывается
отдельно. Вывод содержит действующие коды: сохраняйте его как административные
данные, не публикуйте в общедоступных логах.

Повтор с тем же номером оплаты и теми же параметрами вернёт прежний заказ и
ещё не использованные коды. Новые коды не создаются. Конфликт суммы, количества
или покупателя отклоняется. Это позволяет восстановить результат при потере
соединения после записи заказа. Старый `add-codes` оставлен для бесплатных и
тестовых выдач: **он не регистрирует покупку** и не попадает в партнёрские продажи.
Исторические продажи автоматически не импортируются.

## Возвраты

После реального полного возврата денег:

```bash
node --env-file=.env src/manage.mjs refund-order bank-20261019-0001
```

Команда только фиксирует возврат в учёте: сама деньги не переводит. Неиспользованные
коды заказа деактивируются, заказ исключается из оплаченной статистики. Повтор
безопасен. Уже активированные восстановления автоматически не отзываются.
Частичные возвраты пока не поддерживаются. Привязка пригласившего не меняется.

## Что хранится в MySQL

- `apprevive_partners`: Apple ID в виде существующего идентификатора-хеша,
  уникальный публичный партнёрский код, дата регистрации.
- `apprevive_referrals`: покупатель, пригласивший, дата привязки. Один покупатель
  может иметь только одного пригласившего.
- `apprevive_orders`: уникальный номер оплаты, покупатель, партнёр на момент
  покупки, количество кодов, сумма в копейках, paid/refunded, дата.
- `apprevive_order_codes`: хеши выпущенных кодов и соответствующий заказ.
  После активации исходный код удаляется из активной таблицы, как раньше.

Администратор может посмотреть, кто от кого пришёл и что купил:

```sql
SELECT r.buyer_id, p.referral_code, r.created_at
FROM apprevive_referrals r
JOIN apprevive_partners p ON p.account_id=r.partner_id;

SELECT o.payment_reference, o.buyer_id, p.referral_code,
       o.quantity, o.amount_kopecks, o.state, o.created_at
FROM apprevive_orders o
LEFT JOIN apprevive_partners p ON p.account_id=o.partner_id
ORDER BY o.created_at DESC;
```

Публичный API разрешает только `/v2/partner/profile` и `/v2/partner/bind`.
Операции продажи и возврата доступны только серверной командой. База и её
пароль в приложение не попадают. Резервные копии этих таблиц нужны вместе
с резервными копиями серверных балансов и промокодов.

## Вознаграждения и дальнейшее подключение платежей

Процент, фиксированная сумма за код, правила выплат и скидки не заданы,
поэтому вознаграждения сейчас **не начисляются и не выплачиваются**. Хранится
проверяемый учёт оплаченных заказов; размер вознаграждения можно добавить после
согласования правил. При подключении шлюза подтверждённый и проверенный webhook
должен вызывать ту же `recordPurchase` с уникальным ID платежа. Нельзя считать
нажатие «Оплатить», клиентский запрос или активацию кода подтверждением оплаты.

Действуют ограничения текущей идентификации Apple ID, описанные в инструкции
Node API: сервер получает хеш адреса из штатного клиента, а не независимое
доказательство владения Apple ID. Он не защищает от специально подделанных
запросов. Перед автоматическими денежными выплатами требуется отдельная
серверная аутентификация и правила против злоупотреблений; обычный сброс кеша
штатного приложения партнёрскую привязку не сбрасывает.
