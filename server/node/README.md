# AppRevive API — Node.js + MySQL, подключение по HTTP и IP

AppRevive → `http://185.173.93.200:3000` → Node.js → MySQL.
Домен и сертификат не обязательны. В клиенте находится только публичный адрес API. Пользователи не получают пароль или имя пользователя MySQL; Apple ID и пароль Apple в этот API не отправляются.
HTTP не шифрует промокоды и идентификатор установки. При необходимости позже можно включить HTTPS без изменения таблиц.

## Что нужно на сервере

Node.js 24 LTS или 26, доступ к вашей существующей MySQL 5.7+, открытый TCP-порт 3000. VPS или хостинг с поддержкой постоянно работающего Node.js-процесса. Обычного доступа к MySQL/phpMyAdmin недостаточно для запуска сервера.

## 1. Установить сервер

На сервере из корня исходников:

```bash
cd server/node
npm ci
cp -n .env.example .env
chmod 600 .env
nano .env
```

В `.env` заполните реальные реквизиты **только на сервере**:

```dotenv
HOST=0.0.0.0
PORT=3000
ALLOW_HTTP=true
DB_HOST=ВАШ_СЕРВЕР_MYSQL
DB_PORT=3306
DB_USER=ВАШ_ПОЛЬЗОВАТЕЛЬ
DB_NAME=ВАША_БАЗА
DB_PASSWORD="ВАШ_ПАРОЛЬ"
DB_SSL_CA=
```

HOST — адрес прослушивания Node.js; DB_HOST — отдельный адрес MySQL. Это разные параметры. Публичный IP Node.js также может отличаться от IP MySQL. Символ `#` в пароле требует кавычек в `.env`.
`.env` исключён из Git; не отправляйте его пользователям. DB_SSL_CA необязателен: путь к сертификату CA для проверенного TLS-соединения с MySQL. Не отключайте проверку сертификата, если указываете CA.

## 2. Таблицы

Используются прежние таблицы и существующие коды; новая база не нужна. Если таблицы уже созданы, этот шаг можно пропустить.
В mysql-клиенте выберите свою базу и импортируйте из корня проекта:

```sql
source server/promo/schema.sql;
source server/promo/catalog-schema.sql;
source server/promo/catalog-seed.sql;
```

Пути относительны папке, из которой запущен mysql-клиент. В схеме нет удаления таблиц. Существующие квитанции активаций сохраняются, коды из них не становятся действительными снова.
У пользователя Node.js нужны SELECT/DELETE на `apprevive_promo_codes`, SELECT/INSERT на `apprevive_promo_redemptions`, SELECT на `apprevive_app_catalog`. Для CLI-команд администратора дополнительно INSERT на коды и UPDATE на каталог.

## 3. Запуск и проверка

```bash
npm start
```

В другом терминале сервера:

```bash
curl http://127.0.0.1:3000/health
curl http://127.0.0.1:3000/v1/catalog
```

Затем с Mac проверьте `curl --max-time 10 http://185.173.93.200:3000/health`. Ожидается `{"status":"ok"}`. `/health` проверяет процесс; подключение к MySQL проверяется при запуске сервера. Каталог проверяет запрос к таблице.

Для постоянной работы на Linux можно создать службу systemd. Пример `apprevive-api.service` лежит в `deploy/`: замените пользователя и путь, установите файл в `/etc/systemd/system/`, затем выполните `sudo systemctl daemon-reload` и `sudo systemctl enable --now apprevive-api`. Путь к Node.js проверьте через `command -v node` и при необходимости измените ExecStart. Служба читает `.env` через Node.js, а не через systemd: поддерживаются те же кавычки и формат, что у `npm start`.

Если входящие подключения блокируются, разрешите TCP 3000 в firewall VPS и панели провайдера. MySQL-порт открывать пользователям приложения больше не нужно; его доступ можно ограничить IP вашего Node.js-сервера после перехода всех клиентов.

## 4. Встроенный адрес приложения

В `apprevive_core/api_settings.json` уже указано:

```json
{
  "base_url": "http://185.173.93.200:3000"
}
```

Адрес `http://185.173.93.200:3000` уже записан в исходниках для Mac и Windows. Этот файл с одним публичным URL входит в `.app` и `.exe`; пароль MySQL там отсутствует. Для Windows через GitHub Actions изменение URL должно быть закоммичено в выбранную ветку перед запуском сборки.
После пересборки пользователям не нужен ни `mysql.json`, ни отдельная настройка API.

Для проверки без пересборки можно создать `~/.apprevive/api.json` на Mac или `%USERPROFILE%\.apprevive\api.json` на Windows с тем же JSON. Этот файл переопределяет встроенный адрес. Ещё выше приоритет `APPREVIVE_API_URL`. Изменения применяются после перезапуска приложения.
Старый `mysql.json` приложение больше не читает. Старые уже скачанные сборки с прямым MySQL необходимо заменить новой; эта правка не меняет их автоматически.

## 5. Управлять кодами и иконками

На Node.js-сервере, из `server/node`:

```bash
npm run add-codes -- 200
npm run sync-icons
```

Первая команда создаёт 200 случайных кодов в базе и выводит их в терминал администратора. Вторая находит картинки Apple в RU/US и заполняет пустые `icon_url`; ручные картинки не перезаписывает. Для удалённых приложений можно записать HTTPS-адрес картинки вручную в `apprevive_app_catalog.icon_url`. При отсутствии изображения приложение использует встроенную картинку.

## API

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/health` | Проверка процесса |
| GET | `/v1/catalog` | Публичный список: ID, название, адрес картинки |
| POST | `/v1/redeem` | Погашение одного кода |

POST JSON: `code`, `installation_token` (64 hex), `request_id` (32 hex). Ответ: `status: activated`, `credits: 1`, SHA256 кода и тот же request_id. В HTTP нет ручек для SQL, удаления таблиц, выдачи паролей или получения Apple ID.

Удаление кода и сохранение подтверждения идут одной транзакцией InnoDB. Повтор после потери ответа возвращает прежнее подтверждение. Сохраняются старые локальные баланс/запросы и серверные квитанции. Первое бесплатное восстановление и баланс по-прежнему локальные: API обеспечивает одноразовое погашение, а не защиту от модификации клиентского приложения.

На активацию действует лимит 20 запросов за минуту с IP, тело запроса — до 4 КБ. На один серверный процесс; при масштабировании нужен общий лимитер. За обратным прокси заголовок X-Real-IP принимается только от loopback; прокси обязан перезаписывать его. Ошибки не возвращают SQL и реквизиты.

## Серверный баланс Apple ID (обязательное обновление API)

Новые Mac/Windows клиенты используют `/v2/account/balance`, `redeem`, `reserve`,
`finish`. MySQL хранит один первоначальный подарок на аккаунт, остаток и число
успешных восстановлений. Сессии Apple и история покупок на сервер не передаются.

Обновление сервера (из корня существующего git-клона):

```bash
git pull --ff-only
mysql --host=shuloquaticu.beget.app --port=3306 --user=apple --password --database=apple < server/promo/schema.sql
mysql --host=shuloquaticu.beget.app --port=3306 --user=apple --password --database=apple < server/promo/accounts-schema.sql
cd server/node
npm ci --ignore-scripts
sudo systemctl restart apprevive-api
```

Пароль вводится в приглашении mysql; файл `.env` остаётся прежним. Если клиент
mysql отсутствует на сервере, импортируйте оба SQL-файла через панель MySQL.
Если API запускался вручную, остановите прежний процесс и выполните `npm start`.
Не запускайте второй процесс на уже занятом порту 3000.

Таблицы:

- `apprevive_accounts`: `account_id` (SHA-256 нормализованного адреса Apple ID с
  префиксом `apprevive-account-v1:`), `credits` (остаток, первоначально 1),
  `installations` (число подтверждённых успешных установок), время создания.
- `apprevive_restorations`: аккаунт, уникальный запрос, состояние
  `reserved` / `completed` / `failed`, время начала.
- Существующие таблицы промокодов сохраняются. Активация кода и начисление
  серверного восстановления выполняются в одной транзакции.

При начале установки кредит резервируется. Подтверждённая ошибка возвращает его
ровно один раз; успех увеличивает счётчик ровно один раз. Параллельные установки
на другом компьютере не могут потратить тот же кредит. Без API новые клиенты
не устанавливают приложения и не выдают локальный подарок.

При обрыве сети после установки клиент сохраняет итог для повторного
подтверждения. Если приложение аварийно завершилось во время установки или
пользователь удалил локальные файлы повторов, резерв остаётся на сервере:
автоматически возвращать его нельзя, поскольку установка могла завершиться.
Администратор должен проверить результат и закрыть резерв через API `finish`
с соответствующим `success`; не удаляйте строки аккаунтов для восстановления
доступа. Список спорных операций:

```sql
SELECT account_id, request_id, created_at
FROM apprevive_restorations WHERE state='reserved';
SELECT account_id, credits, installations FROM apprevive_accounts;
```

### Границы защиты и переход со старых версий

Идентификатор строится из Apple ID, прочитанного из текущей авторизованной
сессии ipatool. Очистка файлов и переустановка штатного клиента не меняют этот
идентификатор. Пароль Apple не отправляется API. Хеш адреса не является секретом
или доказательством владения аккаунтом: специально изменённый клиент может
подделать запрос. Для защиты от этого нужна самостоятельная серверная
аутентификация/подтверждение пользователя. При HTTP запросы также не защищены
от перехвата и изменения.

При смене самого адреса Apple ID нужна ручная миграция серверной записи: эта
версия не использует постоянный DSID Apple. Старые локальные остатки и историю
невозможно достоверно восстановить задним числом; они автоматически не
импортируются. Каждый впервые зарегистрированный сервером Apple ID начинает
с одного подарка. Старые выпущенные версии с локальным учётом нельзя удалённо
сделать защищёнными: распространение их следует прекратить и заменить новыми.
