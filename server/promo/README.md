# AppRevive: одноразовые коды через MySQL

Приложение отправляет код HTTPS-запросом на серверный PHP API. Только API
подключается к MySQL. Пароль БД отсутствует в приложении и исходниках.
При активации код удаляется из `apprevive_promo_codes`, а квитанция записывается
в `apprevive_promo_redemptions` в одной транзакции InnoDB.

**Статус:** серверные файлы и клиент подготовлены; на вашем хостинге они ещё
не размещены. Рабочее подключение к вашей БД не подтверждено. Одних данных
MySQL недостаточно для загрузки PHP-файлов на сайт: требуется файловый
менеджер Beget, SFTP или SSH.

## Что нужно

- Сайт с HTTPS, PHP 8.1+ и расширением PDO MySQL (`pdo_mysql`).
- MySQL/MariaDB с InnoDB; ваша существующая база и её полное имя в панели.
- Доступ к файлам сайта и phpMyAdmin или возможность выполнить SQL.
- Подтверждённые параметры подключения из раздела MySQL в Beget.

Сверьте `host`, порт и полное имя базы в панели Beget. Пользователь MySQL
часто совпадает с полным именем базы. Переданные вами параметры подключения
не включены в публикуемые файлы: шаблон содержит только заполнители.

## 1. Создайте таблицы

В phpMyAdmin откройте нужную базу и импортируйте `schema.sql`.
Скрипт создаёт только две таблицы с префиксом `apprevive_promo_` и не удаляет
другие таблицы или данные. Таблицы должны использовать InnoDB.

- `apprevive_promo_codes`: действующие коды. Поле `code` — код с точным
  совпадением регистра; нажатие Enter не является частью кода.
- `apprevive_promo_redemptions`: история активаций с хешем кода, хешем
  идентификатора установки и ID запроса. Квитанции нужны для повторных
  запросов после сетевого сбоя; не удаляйте их вместе с действующим кодом.

## 2. Разместите файлы

Пример структуры на хостинге:

```text
каталог_сайта/
    apprevive-promo-private/
        config.php
        service.php
        manage.php
    public_html/
        apprevive/
            redeem.php
```

1. Файл из `public/redeem.php` загрузите в `public_html/apprevive/redeem.php`.
2. Рядом с `public_html`, вне публикуемой папки, создайте
   `apprevive-promo-private`.
3. Скопируйте туда `private/service.php` и `private/manage.php`.
4. Скопируйте `private/config.example.php` как `config.php` в эту приватную
   папку и отредактируйте **на сервере**.
5. Укажите реальный пароль только в `config.php`. Этот файл исключён из Git.

Если структура сайта отличается, задайте серверную переменную
`APPREVIVE_PROMO_PRIVATE_DIR` с абсолютным путём к приватной папке.
Переменная настраивается на сервере, не в приложении пользователя.

Параметры `config.php`:

| Параметр | Значение |
|---|---|
| `db_dsn` | `mysql:host=АДРЕС;port=3306;dbname=ПОЛНОЕ_ИМЯ;charset=utf8mb4` |
| `db_user` | Полный пользователь MySQL из панели Beget |
| `db_password` | Пароль, установленный только на сервере |
| `db_ssl_ca` | Абсолютный путь к сертификату CA внешнего сервера MySQL |
| `db_private_network` | `true` только для проверенной приватной сети с IP RFC1918 |

Для MySQL на том же сервере можно указать `host=localhost` и пустой
`db_ssl_ca`. Для облачного сервера на публичном адресе получите CA у хостера:
API проверяет сертификат MySQL. Для приватной сети Beget укажите именно
приватный IP вида `10.x.x.x`, `172.16–31.x.x` или `192.168.x.x`, пустой
`db_ssl_ca` и `db_private_network=true`. Не отмечайте публичный адрес как
приватную сеть. Доступ к БД нужно разрешить для сервера API.

Приложение будет использовать:

```text
https://sv-bz.ru/apprevive/redeem.php
```

Если выбрали другой сайт/путь, перед запуском из исходников задайте
`APPREVIVE_PROMO_API_URL`. Для распространяемого приложения измените
`PROMO_API_URL` в `apprestore_core/restoration_codes.py` и пересоберите `.app`/
`.exe`. На каждом компьютере MySQL настраивать не нужно.

Связь приложения с API по-прежнему использует HTTPS: на сайте должна быть
правильно установлена цепочка SSL-сертификатов. Перенос кодов в БД сам по
себе не меняет сертификат сайта.

## 3. Добавляйте коды

### Через phpMyAdmin

Откройте таблицу `apprevive_promo_codes`, вкладку «Вставить», и заполните
поле `code`. Для каждого нового кода создайте одну строку. Не добавляйте
повторно код, который уже использован: квитанция сохраняется в истории.

Пример добавления **собственного нового** кода через SQL:

```sql
INSERT INTO apprevive_promo_codes (code) VALUES ('ВАШ-НОВЫЙ-КОД');
```

API не выдаёт список кодов и не имеет публичного обработчика добавления.

### Генерация по SSH

Из приватной папки выполните:

```bash
php manage.php generate 10
```

Скрипт создаст 10 случайных кодов вида `RV-...`, добавит их в базу и выведет
в вашем административном терминале. Эти коды можно выдавать пользователям
через Telegram.

### Импорт прежнего текстового списка

Сначала сохраните собственную копию списка в приватном каталоге сервера:

```bash
php manage.php import /абсолютный/путь/promo.txt
```

Формат импорта — UTF-8, один код на строку. Пустые строки и дубликаты
пропускаются; известные серверу использованные коды не возвращаются в оборот.
Исторические локальные активации старых версий нельзя автоматически узнать
из текстового файла: импортируйте только коды, которые хотите оставить
действующими.

После перехода закройте публичный `uploads/promo.txt`, чтобы старые версии
не продолжали выдавать восстановления по прежнему списку. Новый клиент
вообще не читает этот файл и не откатывается к нему при ошибке API.

## 4. Проверка

Открытие URL в браузере делает GET и возвращает `405 method_not_allowed`:
это ожидаемо, код активируется только POST-запросом. Для проверки создайте
отдельный одноразовый тестовый код и активируйте его из новой сборки.

После успешного ввода:

1. Запись кода исчезает из `apprevive_promo_codes`.
2. В `apprevive_promo_redemptions` появляется одна квитанция.
3. В приложении начисляется одно восстановление и продолжается ожидавшая
   операция. Неудачная установка оставляет восстановление доступным.
4. На другом компьютере тот же код не принимается.
5. Повтор того же запроса после потери ответа получает прежнюю квитанцию,
   а не списывает второй код. Клиент также не начисляет повторное восстановление.

Если серверный код настроен неправильно или БД недоступна, API отвечает
`503 unavailable`, не раскрывая пароль, SQL, пути или сами коды. Проверьте
серверный журнал PHP и параметры подключения. `404` обычно означает, что
файл API ещё не загружен по указанному адресу. HTML вместо JSON означает,
что запрос попал на страницу сайта/ошибки, а не в API.

Существующий локальный остаток восстановлений и использованные локальные
коды сохраняются. Один первоначальный подарок остаётся локальным, как в
предыдущей версии; эта доработка переносит на сервер погашение промокодов.

## Разработка и проверка

Проверка синтаксиса:

```bash
php -l public/redeem.php
php -l private/service.php
php -l private/manage.php
php -l private/config.example.php
```

Тесты выполняют тот же PHP-обработчик транзакции на изолированной SQLite-базе.
Нужны PHP CLI, PDO SQLite и тестовые зависимости Python:

```bash
python -m pytest -q tests/test_promo_server.py tests/test_restoration_codes.py tests/test_restoration_codes_gui.py
```

Они проверяют единственного победителя параллельных активаций, повтор
одного запроса, откат удаления при сбое записи квитанции, защиту ID запроса,
точное сравнение кодов, восстановление после потери ответа и начисление
только одного локального восстановления. Проверка на настоящем MySQL
и развёртывание на вашем хостинге отдельно обязательны: они пока не выполнены.

Официальные справки: [MySQL в Beget](https://beget.com/ru/kb/manual/mysql),
[транзакции PDO](https://www.php.net/manual/en/pdo.begintransaction.php).
